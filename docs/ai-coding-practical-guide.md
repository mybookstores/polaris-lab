## 第一部分：工具选型——别再纠结了，看场景下菜

社区里最常见的月经问题就是"Cursor 和 Copilot 到底选哪个"。我的答案是：**它们根本不是同一类东西，你可能全都需要。**

### 1.1 先分清三种"物种" ⭐

很多新手把工具混为一谈，其实 AI 编程工具分三层：

| 类型 | 代表产品 | 一句话比喻 | 适合场景 |
|---|---|---|---|
| **代码补全 (Autocomplete)** | GitHub Copilot、Cursor Tab | 你打字它接话的"输入法 Plus" | 写重复代码、补全函数、写测试 |
| **对话/Agent IDE** | Cursor、Windsurf、Trae | 能读你项目、能改多个文件的"实习生" | 从 0 做功能、跨文件重构 |
| **终端 Agent (CLI)** | Claude Code、Codex CLI、Gemini CLI | 能自己跑命令、跑测试、提 PR 的"远程同事" | 自动化任务、批量迁移、无人值守跑活 |

> 💡 **关键认知**（来自 Anthropic 官方）：像 Claude Code 这类 Agent 工具，和聊天机器人的本质区别在于——"你不再是自己写代码然后让 AI review，而是描述你想要什么，让 AI 自己去探索、规划、实现"。这句话值得贴墙上。
> 来源：[Claude Code Best Practices](https://code.claude.com/docs/en/best-practices)

### 1.2 主流工具横评（2025-2026 社区口碑综合） ⭐⭐

**适用场景：正在选工具 / 想给团队采购**

- **Cursor** — 目前综合体验第一梯队，社区讨论量最大。
  - 👍 优点：Tab 补全极强（能预测你下一步要跳哪、改哪），Composer/Agent 模式改多文件顺滑，`.cursorrules` 生态成熟。
  - 👎 吐槽：贵（社区高频抱怨额度/定价），大项目上下文有时会"抽风"。
  - 社区共识：**新手到中级最推荐的一站式工具**。

- **GitHub Copilot** — 老牌稳健，背靠微软和 GitHub。
  - 👍 官方明确它最擅长：*写测试、写重复代码、debug 和纠正语法、解释代码、生成正则表达式*。
  - 👎 官方也坦白它不擅长：*非编程问题、以及"替代你的专业判断"*。
  - 一句话："**你才是老板，Copilot 是趁手的工具**"（这是 GitHub 官方原话的意思）。
  - 来源：[GitHub Copilot Best Practices](https://docs.github.com/en/copilot/get-started/best-practices)

- **Claude Code / Codex CLI** — 硬核玩家最爱。
  - 👍 优点：终端里就能干活，能自己跑测试、提 PR，可无人值守、可并行多开、可进 CI。适合"把任务扔给它然后去喝咖啡"。
  - 👎 门槛：偏命令行，新手需要适应；Token 消耗需要精打细算。

- **Windsurf** — 主打"心流"，Agent（Cascade）自动化程度高，界面友好，被不少人认为对新手更"无感丝滑"。

- **Trae（字节）/ 通义灵码 / 文心快码 / CodeGeeX** — 国产阵营。
  - 👍 优点：**免费额度香、中文语境友好、网络稳定**（不用折腾代理），国内公司合规场景首选。
  - 社区共识：预算敏感、或公司有数据合规要求的，优先看国产。

> 🎯 **选型口诀**：
> 新手想要一把梭 → **Cursor / Windsurf / Trae**
> 已经重度用 GitHub、想稳 → **Copilot**
> 想搞自动化/批量/进阶玩法 → **Claude Code / Codex CLI**
> 预算紧张 or 国内合规 → **国产工具**
>
> 别做工具原教旨主义者，社区里真正的高手往往是"补全用 Cursor Tab，复杂任务开 Claude Code，日常小修用 Copilot"混搭。

## 第二部分：Prompt 编写——决定成败的 70%

社区有句被说烂但极其正确的话：**"你的 Prompt 有多烂，AI 的代码就有多烂。"** 官方文档也反复强调同一件事：**具体，具体，再具体。**

### 2.1 黄金法则：把"许愿"改成"下需求单" ⭐

Anthropic 官方给了一组绝佳的"改造前 vs 改造后"对比，我原样搬来（这是全网最实用的 Prompt 示范之一）：

| 技巧 | ❌ 差的说法 | ✅ 好的说法 |
|---|---|---|
| **限定范围** | "给 foo.py 加测试" | "给 foo.py 写测试，覆盖用户已登出的边界情况，别用 mock" |
| **指明来源** | "为啥这个 API 这么怪" | "去翻 ExecutionFactory 的 git 历史，总结这个 API 是怎么演变成现在这样的" |
| **引用现有模式** | "加个日历组件" | "先看首页现有组件怎么写的，HotDogWidget.php 是个好例子，照着这个模式实现一个日历组件……只用项目里已有的库" |
| **描述症状** | "修一下登录 bug" | "用户反馈会话超时后登录会失败，检查 src/auth/ 里的 token 刷新逻辑，先写一个能复现问题的失败测试，再修" |

> 来源：[Claude Code Best Practices](https://code.claude.com/docs/en/best-practices)

**看出规律了吗？** 好 Prompt = **动作 + 具体对象/文件 + 约束条件 + 验收标准**。

### 2.2 万能 Prompt 模板（可直接抄） ⭐⭐

**适用场景：日常写功能**

```
【背景】我在做一个 [项目类型]，技术栈是 [框架/语言]。
【任务】请实现 [具体功能]。
【参考】请仿照 @[现有文件] 的写法和风格。
【约束】
- 只用项目已有的依赖，不要引入新库
- 遵守 [代码规范，如 ESLint / 命名约定]
- 处理这些边界情况：[列举]
【验收】写完后运行 [测试命令]，确保通过；给我看测试输出。
```

**万能"修 Bug"模板：**
```
【症状】[描述现象 + 报错信息，直接贴 log]
【怀疑位置】可能在 [文件/模块]
【要求】先写一个能复现该 bug 的失败测试，再修复根因（不要只是把错误吞掉/绕过）。修完让我看到测试从红变绿。
```

### 2.3 让 AI 先"采访"你，而不是急着写 ⭐⭐⭐

这是官方一个被严重低估的神技巧。做大功能前，别急着让它写，先让它反问你：

```
我想做 [简短描述]。请用提问的方式详细采访我。
问技术实现、UI/UX、边界情况、我可能没考虑到的权衡取舍。
别问显而易见的问题，专挑难点问。
把我们讨论清楚的东西写成一份完整的 SPEC.md。
```

然后**开一个全新会话**，拿着这份 SPEC 去执行。
> 官方原话精髓："花时间把 spec 写精确，比花时间盯着它写代码更值。"
> 来源：[Claude Code Best Practices](https://code.claude.com/docs/en/best-practices)

### 2.4 GitHub 官方 4 条 Prompt 铁律 ⭐

1. **拆解复杂任务**（别指望一句话生成整个 App）
2. **明确你的需求**
3. **给例子**（输入数据、期望输出、参考实现）
4. **自己也要守好编码规范**（你项目越规范，它学得越像）

> 来源：[GitHub Copilot Best Practices](https://docs.github.com/en/copilot/get-started/best-practices)

### 2.5 社区实战小技巧合集 ⭐⭐

**（以下为小红书/知乎/掘金/Reddit 高频出现的经验归纳）**

- **给它"人设"**：Copilot 官方都建议——"告诉它你是一个极其在意代码质量、可读性和效率的资深 C++ 工程师，然后让它 review 代码"。人设能显著改变输出风格。
- **英文 Prompt 往往质量更高**：模型训练语料以英文为主，写核心 Prompt 用英文常常更精准（这是社区高频经验，尤其在复杂任务上）。中文交流没问题，但关键术语用英文更稳。
- **"少数示例"胜过千言万语**：给 1-2 个 input/output 例子，比写一大段描述有效得多。
- **让它给多个方案**："给我 3 种实现思路，分别说优缺点，我来选"——避免它一条道走到黑。

## 第三部分：让 AI 产出高质量代码的核心内功——上下文管理

如果说 Prompt 是招式，**上下文管理就是内功心法**。Anthropic 官方几乎把整篇最佳实践都建立在一句话上：

> **"几乎所有最佳实践，都源于一个约束：Claude 的上下文窗口填满得很快，而且越满，性能越差。"**

这条对所有 AI 工具都成立。理解它，你就超过 90% 的人了。

### 3.1 上下文会"变脏"，要主动打扫 ⭐⭐

**适用场景：一个会话聊久了 AI 开始变傻/答非所问**

官方点名了几个"翻车现场"，我给你翻译成人话：

- **"大杂烩会话"**：你先聊 A 任务，中途插一句问 B，又回来搞 A。结果上下文全是垃圾。
  → **对策：不相关的任务之间，用 `/clear` 清空重来。**（Cursor 里就是开新对话/New Chat）

- **"反复纠正"陷阱**：它错了你纠正，还错，再纠正……此时上下文已经被一堆失败尝试污染了。
  → **官方铁律：同一个问题纠正超过 2 次，别再纠了！`/clear` 清空，带着你刚学到的教训，重新写一个更好的初始 Prompt。** 一个干净会话 + 好 Prompt，几乎永远优于一个又臭又长、堆满纠错的会话。

- **"无限探索"**：你让它"研究一下 X"却不限定范围，它读了几百个文件把上下文撑爆。
  → **对策：明确圈定范围，或者用子 Agent（subagent）去探索。**

### 3.2 精准喂料：`@` 引用、贴图、管道 ⭐

- 用 `@文件名` 直接引用文件，别用嘴描述"那个在 utils 里的函数"。
- **直接贴截图**：改 UI 时，把设计稿截图丢进去，让它"照着这个实现，然后自己截图对比，列出差异再修"。
- **管道喂数据**：`cat error.log | claude` 直接把报错日志灌进去。
- Copilot 侧同理：**打开相关文件、关掉无关文件**——因为它会拿你打开的文件当上下文。这是 Copilot 官方明确建议的。

### 3.3 用"记忆文件"给 AI 立规矩 ⭐⭐

这是让 AI **持续**产出符合你项目风格代码的杀手锏。不同工具叫法不同，原理一样：

- Claude Code → `CLAUDE.md`
- Cursor → `.cursorrules` / `.cursor/rules`
- 通用 → `AGENTS.md`（越来越多工具在支持这个统一标准）

**官方给的"该写 vs 不该写"清单极其精辟：**

| ✅ 应该写进去 | ❌ 别写进去 |
|---|---|
| AI 猜不到的 Bash 命令 | AI 读代码就能懂的东西 |
| 和默认不同的代码风格规则 | 语言的标准约定（它早会了） |
| 测试怎么跑、用哪个 test runner | 详细 API 文档（放链接就行） |
| 分支命名、PR 规范 | 频繁变动的信息 |
| 项目特有的架构决策 | 长篇大论的教程 |
| 环境变量等"环境怪癖" | "要写整洁代码"这种废话 |

> ⚠️ **反直觉的坑**：规则文件**不是越长越好**！官方警告——"文件太长，Claude 会忽略掉一半，因为重要规则淹没在噪音里了"。判断标准是每一行都问自己："删掉这条，AI 会不会犯错？" 不会就删。
> 想让某条规则被重视，可以加 `IMPORTANT` 或 `YOU MUST` 强调。
> 来源：[Claude Code Best Practices](https://code.claude.com/docs/en/best-practices)

**一个精简的 CLAUDE.md 示例（官方风格）：**
```md
# 代码风格
- 用 ES modules (import/export)，别用 CommonJS (require)
- 尽量解构导入，如 import { foo } from 'bar'

# 工作流
- 改完一批代码后务必做类型检查
- 为了性能，优先跑单个测试，别动不动跑全量测试套件
```

### 3.4 探索先行，规划其次，编码最后（Explore → Plan → Code） ⭐⭐⭐

官方推荐的黄金四段式工作流，堪称"防止 AI 解错题"的核心方法：

1. **探索**（Plan Mode）：只读文件、只回答问题，不许改代码。"读一下 /src/auth，搞懂我们怎么处理会话和登录的。"
2. **规划**：让它出详细方案。"我要加 Google OAuth，需要改哪些文件？会话流程怎么走？做个计划。"
3. **实现**：切出 Plan Mode，让它照计划写，边写边对照。
4. **提交**：让它写描述性的 commit message 并开 PR。

> 但官方也很务实地补了一句：**改个错别字、加行日志、重命名变量这种"一句话能说清 diff"的小活儿，别搞什么规划，直接让它干。**

## 第四部分：真实开发场景实战案例

理论讲完，上硬菜。以下场景配具体操作。

### 4.1 从 0 到 1 做项目 ⭐⭐

**推荐流程（融合官方 + 社区共识）：**
1. 先让 AI **采访你**（见 2.3）→ 产出 `SPEC.md`
2. 开新会话，让它先搭骨架（目录结构、依赖文件、README）
3. **一个模块一个模块地做**，别让它一次生成整个项目（社区血泪教训：一次性生成的大项目往往跑不起来，且没人能 debug）
4. 每完成一个模块，立刻验证（能跑通再进下一个）

### 4.2 重构老代码 ⭐⭐⭐

- 关键动作：**先让它读懂再动手**。"先总结这个模块现在的职责和调用关系，别改代码。" 确认它理解对了，再让它改。
- **小步快跑**：一次重构一个函数/一个文件，配合 git 频繁提交，随时能回滚。
- 用 **Writer/Reviewer 双开**模式（见下）交叉验证。

### 4.3 写测试 ⭐

这是 AI 的**绝对强项**（Copilot 官方钦点）。技巧：
- 明确覆盖目标："覆盖用户登出、token 过期、空输入这三个边界情况"。
- **TDD 反过来玩**：让一个 AI 先写测试，另一个 AI 写代码去通过测试（官方推荐的双 Agent 玩法）。

### 4.4 修 Bug ⭐⭐

**黄金三步（社区 + 官方共识）：**
1. **贴全报错**（别打字复述，直接贴 stack trace / log）
2. **要求先复现**："先写一个能复现这个 bug 的失败测试"
3. **强调修根因**："address the root cause, don't suppress the error"——这句是防止 AI 用 try-catch 把错误吞掉糊弄你的神咒。

### 4.5 上手陌生代码库 ⭐

官方超实用建议：**把 AI 当资深同事直接问**，不需要什么特殊 Prompt：
- "我们的日志系统是怎么工作的？"
- "怎么新建一个 API endpoint？"
- "foo.rs 第 134 行的 `async move { ... }` 是干嘛的？"
- "为什么这里调 foo() 而不是 bar()？"

> 官方说这是最有效的新人 onboarding 方式，能大幅缩短熟悉项目的时间。

## 第五部分：避坑指南——这些坑我替你踩过了

### 5.1 AI 幻觉：一本正经地胡说八道 ⭐

**症状**：调用根本不存在的函数/库、编造 API 参数、引用不存在的文档。
**对策**：
- **凡是它给的代码，必须能验证**。官方的"trust-then-verify gap"（信任但要验证的鸿沟）说得很直白："如果你没法验证它，就别上线它（If you can't verify it, don't ship it）。"
- 给它**可运行的检查**：测试、编译、linter、截图对比。让它自己"写代码→跑检查→读结果→再改"，把验证闭环交给它自己。

### 5.2 安全问题：别把 AI 的代码直接丢生产 ⭐⭐

GitHub 官方三连提醒：
1. **实现前先看懂**它给的代码（看不懂就让它解释）
2. **认真 review**，不光看功能和安全，还要看可读性、可维护性
3. **上自动化工具兜底**：linting、代码扫描、依赖扫描
- 额外：**永远别把 API key、密码等敏感信息贴进 Prompt**（尤其用云端模型时）。可以专门写个 hook「禁止写入 migrations 目录」这类硬约束。

### 5.3 过度依赖：警惕"能力退化" ⭐

这是社区（尤其知乎、HN）讨论最深刻的一点：
- **危险信号**：你开始看不懂自己"写"的代码、离开 AI 就不会写了、盲目接受所有建议。
- **对策**：把 AI 当"结对编程的同事"而不是"外包"。**关键逻辑自己一定要读懂**。GitHub 官方原话："记住你才是主导，Copilot 是为你服务的强力工具。"
- 新手尤其注意：**用 AI 学习，而不是用 AI 替代学习**。多问它"为什么这么写"。

### 5.4 上下文污染（重申，但真的重要） ⭐⭐
- 一个会话别干太多不相关的事。
- 纠错超 2 次就清空重开。
- 规则文件别写成长篇大论。

### 5.5 "过度工程"陷阱 ⭐⭐⭐

一个精妙的高阶坑：当你让 AI **review** 代码时，"一个被要求挑毛病的 reviewer，几乎总能挑出毛病，哪怕代码本来没问题——因为它的任务就是挑刺"。追着每条建议改，会导致过度抽象、防御性代码泛滥。
> **对策（官方）**：明确告诉 reviewer "只标出影响正确性或需求的真问题，其余当作可选建议"。

---

## 第六部分：进阶工作流——把一个 AI 用成一支团队

### 6.1 给 AI 一个"验收标准"，然后走开 ⭐⭐

这是 Anthropic 整篇文档的**第一条核心建议**，重要性拉满：

> "给 Claude 一个它能自己跑的检查：测试、编译、或一张用来对比的截图。这就是'一个你得盯着的会话'和'一个你能走开的会话'之间的区别。"

没有验收标准，AI 只会在"看起来做完了"时停下，而"你"就变成了那个人肉验证循环。给它一个能返回"通过/失败"信号的东西，闭环就自己转起来了。

### 6.2 Writer / Reviewer 双开模式 ⭐⭐⭐

**适用场景：重要功能、想要更高质量**

| 会话 A（写手） | 会话 B（审查员，全新上下文） |
|---|---|
| "给 API 实现一个限流器" | |
| | "review 一下 @rateLimiter.ts，找边界情况、竞态条件、和现有中间件是否一致" |
| "这是 review 反馈：[B 的输出]，去改" | |

**为什么有效**：全新上下文的 reviewer 没有"自己刚写完所以偏袒"的心理包袱，能更客观地挑错。

### 6.3 子 Agent（Subagent）做调研 ⭐⭐⭐

"因为上下文是你的根本约束，子 Agent 是最强工具之一。" 让子 Agent 在**独立的上下文窗口**里去读几十个文件做调研，只把结论汇报回来，你的主对话保持干净。
```
用子 Agent 去调查我们的认证系统是怎么处理 token 刷新的，
以及有没有现成的 OAuth 工具可以复用。
```

### 6.4 并行与规模化 ⭐⭐⭐

真·高阶玩法（适合把 AI 当劳动力集群）：
- **git worktrees 多开**：多个会话在隔离的 checkout 里干活，改动不打架。
- **Fan-out 批量迁移**：写个脚本循环调用 `claude -p "迁移 $file 从 React 到 Vue"`，先用 2-3 个文件调 Prompt，再放大到 2000 个文件。
- **非交互模式进 CI**：`claude -p "修复所有 lint 错误"` 塞进流水线、pre-commit hook。
- **Hooks 硬约束**：CLAUDE.md 的规则是"建议性"的，而 hook 是"确定性"的——"写个 hook，每次编辑文件后自动跑 eslint"。必须每次都发生的事，用 hook。

### 6.5 善用回溯（Checkpoint / Rewind） ⭐⭐
- 大胆让 AI 尝试有风险的方案，不行就 `/rewind` 回退。
- `Esc` 随时打断跑偏的它（上下文保留，可以重新引导）。
- ⚠️ 注意：checkpoint **只追踪 AI 编辑工具做的改动**，Bash 命令改的不算，**它不能替代 git**。

## 第七部分：不同水平，不同打法

### 🐣 新手（写代码 < 2 年 / 刚接触 AI 编程）

- **重点**：用 AI **加速学习**，而不是跳过学习。
- 多用"解释代码"功能，每段生成的代码都问"为什么"。
- 从**小任务**开始：补全、写测试、改小 bug。
- **一定要看懂再用**，看不懂就让它拆解讲解。
- 工具选**开箱即用**的（Cursor / Windsurf / Trae）。
- ⚠️ 最大风险：**能力空心化**。别让 AI 代替你建立编程直觉。

### 🦅 进阶（有经验的工程师）

- **重点**：把 AI 当"团队"而非"工具"——上双开、子 Agent、并行、CI 集成。
- 精修你的 `CLAUDE.md` / `.cursorrules`，让它长期沉淀团队规范（"这个文件的价值会随时间复利增长"）。
- 用 Explore→Plan→Code 处理复杂功能，用 SPEC 驱动开发。
- 建立**验收自动化**（测试/hook/CI），追求"无人值守也能正确完成"。
- 培养直觉：官方说得好——"这些模式不是铁律，是起点。注意什么有效：当 AI 产出很棒时，回想你当时做对了什么。"

## 🎯 新手快速上手清单（照着做，一小时入门）

- [ ] **1. 选一个开箱即用的工具**：Cursor / Windsurf / Trae（国内推荐 Trae/通义灵码，网络稳、有免费额度）

- [ ] **5. 建一个 `CLAUDE.md` / `.cursorrules`**，写 3-5 条你的代码风格和跑测试的命令就够了
- [ ] **6. 养成"看懂再用"的习惯**，看不懂就问"解释这段代码"

- [ ] **9. 让 AI 帮你写测试**（它最擅长的活）
